## 1. 目标、授权与决策责任

目标是可交付的校园资源服务平台：M1 自习座位预约、M2 整教室申请审批、M3 物业报修、D 身份/主数据/通知/审计。优先保证真实业务与跨模块一致性、可迁移数据、可验证 AI 输出和可追溯发布。附加自然语言 Agent 待基础稳定后实现。

2026-10-20/21暂缓安排是历史，原初版74822b9已于10月22日授权推送并邀请协作；TASK-009又按用户明确授权提交5d1a3f7并推送feat/booking-lifecycle。当前feat/admin-management从其继续TASK-010，未人工体验、提交或推送，不代表main合并。未明确规则采用简单初版并记录供体验后调整；外部渠道暂缺时先本地和自动检查，但外部投递仍是待办。云资源/生产发布另行授权，不代成员编造共识或人验。

六人初步职责保持为架构负责人、M1/M2/M3/D 四位模块负责人、交付测试负责人。D 在代码上由独立模块承担，部署上与 M1 位于同一个 core 服务；通知等能力通过明确模块接口提供。该方案减少服务数量，同时保留 D 负责人的独立交付边界。真实姓名、工作量认领、故障责任人和“如何达成组内一致”的过程须由真实成员补充，不能由 AI 编造。

## 2. 候选方案与技术选择

| 候选                                | 优点                                                                                   | 代价与风险                                                                           | 本项目结论                                            |
| ----------------------------------- | -------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------ | ----------------------------------------------------- |
| 单体服务、模块化目录                | 初期最容易启动，单库事务简单                                                           | M2/M3 直接查表容易绕过边界，真实网络集成需额外严格隔离；多人 AI 容易把业务耦合在一起 | 可行候选，未采用为当前主方案                          |
| 两个服务，core=D+M1，workflow=M2+M3 | 调度在一个事务边界；真实 HTTP 集成天然可验；只维护两个后端和两库，适合能力有限的六人组 | 必须处理 HTTP 超时、重复与跨服务状态；D 成为重要依赖，需失败关闭与故障定位           | 当前采用；用持久 outbox、来源版本和行为测试承担复杂度 |
| D/M1/M2/M3 各自微服务               | 自治部署与故障隔离更强                                                                 | 服务发现、跨服务鉴权、分布式追踪、消息和运维负担更重，增加 AI 生成错误面             | 当前不采用；缺乏规模需求，不为“企业化”堆技术          |

当前工具链由实际 package.json/锁文件固定：Node.js 24.22.0、pnpm 10.33.4、TypeScript 5.9.3；前端 Vue 3.5.44/Vue Router/Pinia/Element Plus，Vite 构建；后端 NestJS 12.1.3；Prisma 7.10.0 + pg；PostgreSQL 17，Docker Compose 管理本地数据库。OpenAPI 3.0.3 + openapi-typescript 生成业务 DTO 类型。运行时还必须有 DTO 校验，TypeScript 类型不能校验来自网络的数据。

本轮不用 Java，不改 Python 工作流，不引入 Redis/MQ/Kubernetes。任务和通知的第一版用数据库持久化扫描、租约领取与退避；出现真实吞吐或隔离需求再评估队列。企业级目标依靠事务、权限、迁移、可观测性、恢复和可重复交付实现，不以组件数量判断。

同服务内的模块也不随意互查业务表。D 对 M1 提供 ResourceDirectoryService 等明确服务边界，可在同一 core 数据库事务中读取主数据、检查范围、写审计；M1 只控制自己的资源表。contracts 仅保存协议、客户端与必要基础类型，禁止共享 Prisma 实体/仓储。

每服务单独 Prisma schema、迁移和 seed；结构变更追加新迁移。已执行的core与workflow历史迁移不可改写；TASK-009追加20261023000100_m1_lifecycle，TASK-010再追加20261026000100_d_admin_management；当前core5条迁移22表、workflow3条14表，后者没有新增迁移。`prisma migrate deploy` 依据迁移历史与校验和重复执行；不要求每条 DDL 本身可随意重跑。空库/隔离空 schema 重放和重复 deploy 都须验证，不用删库重建掩盖演进问题。

基础 seed 创建默认配置与服务元数据，create-only 幂等，不覆盖人工编辑。demo seed 是单独、仅本地 development/test 使用的脚本；随机凭据写私密忽略文件，不进入生产和源码。缺少密码文件但已有演示账号时失败，由环境所有者决定恢复/重置，不生成不匹配密码冒充成功。

## 5. M1 唯一资源调度内核

时间统一存 `timestamptz`，输入必须含时区，业务开放规则与展示按 Asia/Shanghai；区间使用左闭右开 `[start,end)`。个人预约只接受未来整点，默认最多 4 小时，配置可调。必须有明确开放规则，演示为每日 08:00～22:00。本人开始前可取消，无额外个人同时预约数量上限。这些是架构负责人确认的初版默认规则。

可用性由启用状态、用户范围、开放规则、个人预约和各来源资源效果共同计算，不存在一个可被任意模块覆盖的全局 available 布尔值。M2 占用仅覆盖申请时段；M3 维修封锁按其确认的有效区间影响全部座位。来源释放只解除对应申请/工单，不能把另一张工单或个人预约一起清除。

写入事务顺序：验证输入和身份 → 取得必要写入幂等/来源锁 → 同一教室事务级 advisory lock → 重新读取主数据、规则和全部占用 → 写资源/回执/审计 → 提交。教室锁命名空间固定为 `room:${roomId}`，通过 PostgreSQL `pg_advisory_xact_lock(hashtextextended(...))` 竞争。所有个人分配、整室占用、维修和相关停用/开放规则变更都必须使用这个入口。数据库同座位重叠排斥约束作为第二道保护，不能用“先查再写”替代事务锁。

事务内不做 HTTP 或外部通知；保持短事务。D 候选读取复用当前事务连接，避免持有连接再申请额外连接导致连接池耗尽。搜索只是当时快照，预约必须再次检查，不能把搜索结果当资源锁。

个人预约公开写请求要求用户作用域内的 UUID 幂等键，指纹含操作和规范化参数；成功结果与业务同事务持久化，参数/操作变化返回冲突。回放返回该命令当时的响应快照，详情 GET 才表示对象当前状态。本轮签到、再次预约、统计和来源详情已实现；其真实失败/权限/边界仍须验证，不能用固定成功响应或接口计数替代验收。

本轮签到/违约采用数据库持久扫描，默认每5秒、每轮最多100项、按ID轮转避免失败队首饥饿。默认签到窗口[-15min,+15min)，前15分钟/后10分钟站内提醒，后15分钟未签取消、释放并记录一次违约；提前提醒0表示关闭。签到与超时竞争同一room锁并在锁后取数据库时间，状态、违约和通知同事务，重启跳过已无意义提醒。旧预约迁移为不追溯处罚，停用或签到窗口受维修影响则免罚；维修首次releasedAt在锁后固定，后续重复释放不延长影响。新预约冻结政策版本/窗口，修改规则不改旧预约；再次预约重检原座位新时段。统计仅为个人座位预约区间小时，已签到小时不是实际在座时长。详细默认与边界见 [TASK-009方案](implementation/task-009-booking-lifecycle.md)。

## 6. M2/M3 工作流与持久任务

本轮 M2 细化与验收范围见 [M2 实现方案](implementation/task-006-m2-workflow.md)。以下为已授权推荐默认政策，不是全组既成共识。

申请人必须拥有当前有效 `m2.applications.create` 和目标教室范围；待审批不预占。政策至少两级，默认院系审批（示例角色 demo-role-department、DEPARTMENT）→ 教室管理员（demo-role-managed、MANAGED_ROOMS），禁止自审与同一人完成多步。角色匹配、该权限范围和当前步骤都必须满足，不可借用其他角色的无关 ALL 权限。demo 角色名只用于本地样本，不能当正式人员认领。

提交保存政策/步骤快照。总截止时间取提交后 48 小时和开始时间较早值；只接受未来整点区间，M2 的时长策略独立于个人预约 4 小时参数；当前限制同一上海自然日、最多 24 小时。本人在使用开始前可撤回。最终审批先记入同步意图，M1 确认占用且 workflow 本地状态提交成功后才批准。

状态区分 PENDING、SYNCING、APPROVED、REJECTED、WITHDRAWN、EXPIRED、RELEASE_PENDING、SYNC_FAILED，并保留目标终态、资源 revision 和错误码。业务状态版本与资源命令版本分别递增。资源冲突进入明确失败状态，不能显示为已批准或在未获授权时任意重新发一个占用命令。

```text
申请 -> PENDING -> 逐步审批 -> SYNCING -> M1确认 -> APPROVED
PENDING -> 驳回 -> REJECTED
未占用的有效撤回/超时 -> WITHDRAWN / EXPIRED
已发出或可能发出占用 -> RELEASE_PENDING -> 确认释放 -> 对应终态
明确资源冲突 -> SYNC_FAILED，保留错误与事实
```

workflow 在同一事务保存业务状态/决定、审计和 outbox，然后提交；工作任务再进行真实 HTTP。outbox 领取使用数据库行锁/租约，有 owner/lease expiry、尝试次数、下次时间与持久结果；重启可接管过期租约。HTTP 操作在事务外执行，结果提交时用当前版本/意图条件更新，迟到回执不能覆盖已经撤回或过期的状态。用户 bearer 仅用于请求时实时授权，不能保存到 outbox、数据库或日志。

占用命令对短暂网络错误以固定 operationId/revision 退避，结果未知先查来源或以原命令核对，有限重试后保留失败事实，未确认不能批准。释放补偿始终保留 RELEASE_PENDING；未知结果以同命令重试，超过 24 次转默认 5 分钟低频。core 已持久化的明确释放失败保留原 FAILED 命令与审计，再同事务追加更高 revision 的释放意图，不冒充原命令成功。释放执行人永久禁用/撤权会持续 RELEASE_PENDING + syncError，只有恢复相应资格后后续补偿才可能收敛；本轮未实现无需人工恢复授权的兜底机制。明确参数错误、501 和凭据配置错误需分类处理，不忙重试。

M3 初版已实现，见 [维修方案](implementation/task-007-m3-workorders.md) 与 `apps/workflow/M3-DESIGN.md`。状态 NEW→ASSIGNED→BLOCK_PENDING→IN_REPAIR→AWAITING_ACCEPTANCE→RELEASE_PENDING→CLOSED；只有当前指派且有效维修人员能开始/完工，来源 ACTIVE 确认后才维修中。验收者有当前管理范围且不是实际维修人，拒绝回维修并保持封锁，通过后确认来源 RELEASED 才关闭。只有报告人具备评价权限可关闭后一次1～5分评价。取消仅限 NEW/ASSIGNED 且封锁意图尚未发出，不能通过取消跳过安全验收。

维修使用真实开始时间，不要求整点，整室无固定终点，和个人/M2竞争同一room锁。已有个人/M2记录保留，多维修叠加，封锁阻止新分配；每张工单仅释放自身来源。M1本人列表/详情增加 maintenanceAffected，界面提示使用安排需人工联系，不能称已自动通知或取消。

SLA 默认响应24h、维修48h、验收24h，政策追加版本且工单冻结快照。响应从创建到封锁确认，维修从封锁确认，验收从完工计时；验收失败形成新维修轮次。升级按 stage+round 唯一，持久保存截止时间、教室、接收人和角色；重启不重复、不自动关闭或解封。事件在工单详情可查，尚未接入 D 外部真实投递。

M3 的公共报修范围与管理动作分开：公共开放可允许跨院系报修；dispatch/repair/accept/管理取消的 DEPARTMENT 只允许用户院系非空且与教室归属匹配。MANAGED_ROOMS/ALL 必须来自对应动作权限，SELF只用于本人取消/评分。core与workflow一致，避免工作流派单通过而资源核心拒绝。工单保存教室院系事实；未来D增加归属/限制写接口前须定义既有工单的重授权/同步，当前不能宣称自动同步。

M3 outbox 同样使用固定命令/时间、租约和本地版本保护。建立明确失败为 SYNC_FAILED，保留命令事实；当前有效指派人可另行 start 发更高版本新意图，未知 BLOCK_PENDING 只重试原意图。释放结果未知持续 RELEASE_PENDING，永久撤权会保留 syncError，不能自动更换操作者绕过权限。

## 7. HTTP 契约、幂等与来源版本

`packages/contracts/openapi.json` 是 DTO 协议源，operationId、x-service、x-permission、x-implementation 与实际实现同步。生成类型不手改。`ResourceCoreClient` 一次调用发送一次请求、固定超时、限制响应大小、不跟随重定向；它不隐藏业务重试。SDK 已有 M2/M3 来源查询、资源命令及双身份上下文，14 项真实 HTTP 测试通过；业务链另由真实双服务测试证明，不能仅因客户端存在方法就算完成。

内部资源命令包含 operationId UUID、sourceModule/sourceId、递增 revision、actorId、reason，建立时另带教室/时间。命令 ID 全局唯一，指纹绑定规范化内容。相同 ID 同内容返回原结果，不同内容 409；明确业务失败也持久化。源版本限制在数据库整数范围内，旧/相同版本的新操作不得覆盖新状态。

释放先于建立也写 RELEASED 墓碑。一个来源生命周期释放后不得以更高版本复活；新的申请/工单需要新的来源 ID。历史成功占用命令在释放后重放仍可能返回当时 ACTIVE 回执，但数据库当前来源仍为 RELEASED；workflow 必须比较当前意图/revision，通过来源 GET 获取当前事实，而非用旧回执回滚本地状态。

跨服务成功至少包含：M1 已提交资源结果、workflow 已提交与当前意图匹配的业务结果。HTTP 超时仅表示调用方未知；不能假定对方没执行并立刻标失败，也不能未经确认标成功。撤回/过期遇到可能已发出的占用时，保存更高版本释放意图与墓碑，保护迟到占用不会复活。

成功返回资源或 items/nextCursor。错误统一 `{error:{code,message,traceId}}`；区分 400 参数、401 身份、403 范围、404 不存在、409 冲突/幂等/旧版本、422 状态、429 限流、501 未实现、503 依赖或结果待确认。分页最大 100；可用性筛选后空页仍可能有 nextCursor，调用方持续到游标为空。

## 8. 身份、权限与安全边界

D 使用 Node crypto 异步 scrypt 和随机盐保存密码；随机 opaque 用户会话仅存 SHA-256 摘要，绝对期限 1 小时。浏览器在 Pinia 内存保存，不写 localStorage/URL；刷新后重新登录。每请求重读用户状态、角色、权限和管理范围。注销、过期、撤权、停用即时拒绝；当前管理用户启停/授权及角色变更同事务撤销相应会话；公开用户注册/改密码尚未提供。

登录失败不区分不存在/停用/密码错误；账号与真实连接 IP 有持久限流，密码计算并发有上限，不信任客户端伪造的 X-Forwarded-For。生产可信代理 IP 规则须单独配置并测试。授权取“该权限”在各角色对应范围的并集，SELF、DEPARTMENT、MANAGED_ROOMS、ALL 不能跨权限串用。

服务凭据与用户会话分开：M2 资源操作只接受 M2 服务身份，另检查实际 actorId 有效、动作权限及教室范围；M3 同理。服务身份只是调用方认证，不证明“申请属于该用户”或“现在轮到该人审批”，这些工作流事实必须在 workflow 验证。双身份内部用户/教室上下文由服务 bearer 和原用户委托共同验证，敏感响应 no-store，前端不能拿到服务凭据。

服务凭据缺失失败关闭，禁止使用默认公开密码。私密 .env、demo 密码文件、Docker 登录信息不进 Git/日志/VITE_*。应用账号不是超级用户且无跨库连接权限。两服务已有 Helmet、严格 CORS/DTO 和统一异常脱敏；生产 HTTPS、密码找回/轮换、备份保留与灾难恢复仍需交付阶段真实配置和演练。

## 9. 通知、审计与运行观测

D本轮已有本人站内通知查询和幂等已读，M1通知与业务状态同事务，按事件/收件人唯一；M3升级事实尚未接成完整通知投递。最终仍须至少一个真实外部渠道，站内记录/控制台日志不能冒充邮件或微信已发送。未来外部投递在事务外执行，保留投递尝试、失败与重试，最少化收件字段；选择渠道及真实凭据配置需环境所有者授权。

业务审计记录 actor/action/target/time/traceId，重要状态同事务写入。跨服务保留原操作者与相关 operationId/sourceId，在各自服务记录，不通过共享审计表破坏数据库边界。普通业务账号不可随意修改历史审计；访问查询按权限范围控制。密码、bearer、签到码和完整请求体不记录。

两服务区分 `/health/live` 和 `/health/ready`：存活不等于数据库就绪，更不等于业务完成。结构化日志包含请求 ID、方法、脱敏路径、响应状态和耗时，查错可从 traceId 关联来源命令；后续补充 outbox 积压/失败、过期租约、通知失败和任务延迟指标，给出可操作告警而非只看日志。

## 10. 环境、CI 与发布

目标流程：任务分支/MR → 安装固定依赖 → lint/类型/契约 → 行为测试与真实数据库集成 → 构建固定版本镜像 → 环境锁 → 测试环境自动迁移/全组部署/冒烟 → 人工批准生产 → tag 对应版本发布 → 健康与关键链验收。失败停止后续阶段，合并规则阻止失败测试；公共接口、D 和 schema 变更需相关成员评审。

`pnpm check` 覆盖结构、lint、类型、SDK 测试、构建和基础服务烟测，不能代替数据库业务验收。CI 还须明确运行实际数据库/身份/调度/工作流测试。测试服务与样本隔离、结束定向清理，禁止重置共享库。迁移在环境级锁内执行，部署和集成测试协调，避免不同模块部署互相打断。

测试部署一次覆盖本组 web/core/workflow，配置/秘密按环境提供。生产保留人工审批、可追溯 tag/提交/镜像摘要和当前版本显示；回退需验证应用与 schema 兼容，优先兼容增量迁移和向前修复，不能假定回退应用等于删除数据库迁移。正式备份/恢复、发布窗口、成本上限和服务器规格待资源授权后落实。

`pnpm dev` 经 `tools/dev-local.mjs` 启动本地三应用：缺少既有凭据时分别生成彼此独立的 M2/M3 随机进程令牌并共享给两后端，并传入本地 core HTTP origin；仅限 development/test、loopback 服务和本地数据库，不改 .env、不保存秘密。既有两端令牌不一致时拒绝；生产禁止使用此启动器，必须正式配置并管理服务凭据。

## 11. 质量、风险与工程伦理

每次任务先写范围、关联需求、允许修改路径、状态/不变量和失败验收，再实现。测试覆盖真实 PostgreSQL/真实 HTTP、越权、并发、乱序、重启和时间边界；不 mock 掉核心业务。至少对关键行为做一次隔离破坏实验，恢复后再次通过。已有真实缺陷包括空范围过滤导致泄露和重复申请连接导致池耗尽，修复与测试证据要保留，不能写成从未发生。

AI 高风险点是隐式越权、无效空过滤、先查后写、超时误判成功、迟到回执覆盖新状态、seed 覆盖密码/授权和假测试。采用严格运行时校验、最小权限、数据库约束、统一锁、原子意图、版本 fence、幂等 seed、真实行为测试和人工验收分别约束。变更不是越多越专业，接口状态与未完成项必须明确。

伦理工作从开发开始记录真实决策：院系限制和资源公平、违约误判及申诉、维修安全优先与既有预约影响、个人信息最少化、审计访问与数据保留、AI 工作的责任归属。当前没有实现申诉、完整保留策略或生产通知，不能声称已解决。每名成员论文基于本人真实任务和证据，AI 不代造个人经历、组内共识、提交或评审。
